# Original-application authorization on Linux

The owner approved an independent Linux authorization-code flow for the original Baidu application: hidden SecretKey and one-time authorization-code entry, separate credentials, read-only MCP verification and real refresh verification. The original Windows user environment no longer exists; the owner can access the application's developer console. Do not attempt offline DPAPI decryption. Preserve the currently working experience authorization and default MCP registrations.

Reuse the original application's non-secret AppKey from the explicitly identified migration configuration, confirmed to match its encrypted SecretKey metadata. Do not publish that machine-local key in Git. New `prepare-app` helper creates `original-app-settings.json` beside deployed settings, with separate `original-app-authorization.json` and `original-app-secret.json`. Rerun preserves existing files and rejects incompatible profiles. All paths remain owner-only, outside source, beneath the same private deployment root.

The authorization command displays the official HTTPS code/OOB URL with a random state. SecretKey and returned code are hidden inputs in a real terminal. A complete official result URL, when supplied, must match the generated state; an OOB page's raw code is accepted only as the user's explicit local entry. Exchange once through a bounded HTTPS POST with no redirect, proxy, automatic retry or credential-bearing diagnostics. Require a valid access token, nonempty refresh token, bounded lifetime and netdisk scope before saving. Reuse existing private-file validation and the refresh lock.

Persist a full private pending authorization bundle before publishing the separate secret/token files. Failed publication retains the bundle and blocks further exchange/refresh until an explicit local recovery command publishes it. Never overwrite pending recovery evidence. Existing credentials require an explicit replacement flag. Manual saves and authorization recovery share the same process-safe lock as refresh. No default token, setting or registration is switched by preparing, authorizing or verifying this profile.

Allow launchers and the installed read-only protocol checker to select alternate settings through the non-secret `BAIDU_MCP_SETTINGS_FILE` environment variable. Node workers inherit the same selection and helper commands consistently use it. No environment variable carries credentials. Windows default behavior remains unchanged.

Tests cover strict URL/code/state handling, once-only exchange and sanitized errors, required refresh/scope, file modes, no default credential changes, pending failure/recovery, separate settings across Node/Python processes, and the existing authorization/relay regression suites. Existing Windows-specific tests remain skipped on Linux and are not relabeled as verified.

After reviewed implementation and checks, merge under standing authorization, deploy from stable main, create the isolated profile using the known AppKey, and hand off hidden SecretKey/code entry to the owner. Only after the owner saves credentials perform installed MCP read-only initialization/root listing and a force-refresh check for this candidate, with no cloud writes. Historical original-app sharing returned invalid app; do not claim sharing equivalence or replace the experience profile. Preserve a private migration/provenance record without credential values.

Builder choices: helper/module names, finite 30-second OAuth timeout, error-code spelling and profile validation internals. This is a small extension to the existing backend, not a new OAuth daemon, browser automation or automatic account switch.
