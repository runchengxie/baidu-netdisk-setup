# 自动刷新令牌与上传断点续传

自动刷新已接入两个 MCP，条件是持有同一应用的刷新令牌、AppKey 和 SecretKey。持久化断点续传尚未接入，需要继续增加任务状态的保存和恢复。

## 自动刷新令牌

Access Token 有有效期。百度官方 OAuth 刷新接口要求四个参数，其中 `grant_type` 固定为 `refresh_token`，另外三个是刷新令牌、所属应用的 AppKey 和 SecretKey。返回的新令牌需要重新加密写入权威授权文件。[官方 OAuth 说明](https://openauth.baidu.com/doc/doc.html)

| 授权情况 | 当前条件 | 可以怎样推进 |
|---|---|---|
| 按本指南取得的官方体验授权 | 文件里目前只有访问令牌，没有刷新令牌，也没有体验应用的 SecretKey | 保留到期提示和人工重新授权流程，不能承诺直接自动刷新 |
| 自己应用的授权 | 需要同一应用的刷新令牌、AppKey 和 SecretKey | 三项齐全后，两个 MCP 自动检查并按需刷新 |
| 有刷新令牌但没保存 SecretKey | 材料仍不完整 | 由应用所有者找回对应密钥，在本机隐藏输入，不能将密钥发到聊天或提交仓库 |

密钥通过 `save-app-secret.ps1` 隐藏输入，使用 Windows 当前用户加密保存在仓库外；`.env` 只记录 AppKey 和文件路径。材料检查通过不等于百度已接受密钥；可以使用 `ensure-authorization.ps1 -Force` 验证真实刷新。

### 已实现的流程

1. 两个 MCP 启动时共用 `ensure-authorization.ps1` 检查有效期。剩余有效期不超过七天才请求刷新；已经过期但刷新材料仍可用时，也会先尝试刷新。
2. 长期运行时每天检查一次；失败后约一小时重试。电脑关机或 MCP 未运行时没有独立后台任务，下次启动再检查。
3. 刷新时独占同一授权文件旁的锁文件，取得锁后再次读取授权。另一个进程刚更新过令牌时，直接采用新结果。锁文件可以长期存在，占用状态由操作系统管理，进程结束后释放。
4. 官方接口返回完整访问令牌、刷新令牌及有效期后，先用 Windows 当前用户加密，再以同目录原子重命名替换权威授权文件。接口失败保留原文件；若最终保存失败，已加密的 `<授权文件名>.pending-refresh.json` 保留在授权目录，工具会阻止再次交换并提示人工恢复，避免丢失服务端已经轮换的新令牌。
5. 本地上传在调用前检查授权变化，整个上传固定使用所选令牌。本进程的后台刷新等待上传结束。远程 MCP 每分钟检查授权文件变化，空闲时更新桥接连接并重新初始化；更新期间的新请求暂存，已执行的写入不会自动重放。
6. 网络或本机故障报告 `network_or_local_failure`，失效授权报告 `reauthorization_required`，密钥被拒绝报告 `app_credentials_rejected`。现有令牌仍有效时可继续使用，到期后启动会停止并提示处理授权。

远程连接更新只用于令牌更新，暂不提供任意网络断线的自动恢复；重新初始化超时会结束 MCP，需由客户端重启。若请求长期没有返回，更新会等待它结束；另一个 MCP 的刷新不会等待此进程正在执行的操作，不承诺跨进程进行中的上传一定不受服务端令牌变更影响。生产连接需要在升级后重启，才能加载新启动程序。

### 需要验证的情况

测试覆盖刷新成功后的加密保存、有效期更新、非临近到期时不交换、过期授权先刷新、材料缺失、应用不匹配、网络失败、无效响应、被拒绝的密钥和失效授权，以及两个进程同时刷新只交换一次。错误响应使用人工测试材料，不更改真实密钥。远程协议测试覆盖等待写入结束、取消请求转发、更新期间暂停新请求及不重放写入。真实接口与 MCP 的验证结果见 [验证摘要](verification.md)。

## MCP 上传断点续传

官方上传程序会把文件分片上传，并对某些失败请求重试。当前程序没有持久化任务状态，关闭程序后不能按原任务继续。

独立测试已经证明官方 API 可以复用保存的上传任务 ID。合成文件大小为 2 GiB + 17 字节，共 513 片，曾在确认 2 片和 358 片后分别中断，另一个进程继续上传剩余分片，最终完整下载 SHA-256 一致。这份能力证明来自私人 API 测试脚本，当前安装的 MCP 仍没有自动续传。[已有验证摘要](verification.md)

### 建议的接入流程

1. 计算本地文件的大小、完整 SHA-256 和分片 MD5。状态记录放在数据目录，包含目标账号、网盘路径、文件指纹和上传任务 ID，不存 OAuth 令牌。
2. 每片上传后，先核对服务器返回的 MD5，再原子保存已确认的分片编号。状态文件写入时加锁。
3. 下次用相同账号上传相同文件到相同位置时，自动寻找匹配的未完成任务，再核对本地文件指纹，复用原上传任务 ID，只补传未确认的分片。
4. 本地内容已变化时停止，说明不能继续原任务。上传任务 ID 失效时明确提示，不把重新从头上传称为成功续传。
5. 最终创建文件后核对结果并标记完成。若服务器可能已创建文件，但客户端没收到响应，先查询实际状态；仅凭同名和大小不能证明是同一份内容，不能盲目覆盖或重复创建。
6. 保留当前默认拒绝覆盖的规则。恢复未完成上传不应当扩大为覆盖其他文件的权限。

这里的“自动续传”是再次调用上传工具时自动找回进度。程序关闭后，不承诺系统会在无人调用的情况下自行启动上传任务。

### 需要验证的情况

先用十几 MiB 的合成文件测试进程中断、重启恢复、文件变化、网络失败、重复调用和状态损坏，再做一次数 GiB 的端到端测试。核对恢复前后的上传任务 ID、跳过的分片、最终文件内容和测试清理情况。

## 下一步建议

下一步可接入持久化续传，它已有完整 API 实测基础，适合经常上传大文件。只有体验授权的使用者继续按照设置指南人工重新授权。
